# skill_catalog — 課題→Skill 提案の元になる知識

`propose_skills(課題マップ, ナレッジ) → 提案リスト` が根拠にする知識ソース。診断で発火したシグナルを課題ラベルに変換した後、このカタログの該当エントリを元に Skills 提案を生成する。

- 提案の単位は「既存 Skill をそのまま導入」ではなく、**既存 Skill をベース・参考にしたカスタム Skill / プロンプトを作る**こと
- 全提案は**未検証の初期仮説**。運用で効果が確認できた提案には `効果実績:` 注記を追記し、生きたナレッジとして更新していく（ベース Skill 側の `運用実績:` は「既に運用されている実例」を指す別の記法）
- シグナル定義・閾値の正は SKILL.md 本体。この表の「検知内容」列は参照用の要約

## ベースにする既存 Skill の出典

| 出典 | 扱い |
|---|---|
| 汎用の開発支援 skill | セルフレビュー・タスク分解・レビュー観点提示など、開発現場で広く使われている型。**特定の配布パッケージを指すものではない**ため、同等の型を各チームの環境で用意することを前提に参照する |
| プロダクト開発チームでの運用実例 | 実際の開発チームで運用されている skill / スラッシュコマンドの構成。`運用実績:` と明記し、仮説ベースの参照と区別する |

このカタログは提案を組み立てるための参照材料として、型の名前と要点だけを持つ。**参照元の skill そのものは配布していない**ため、`運用実績:` の項目は「こういう構成が実運用されている」という設計の手がかりとして読み、自チームの文脈に合わせて作り直すこと。

## 語彙定義（課題マップと共有）

カテゴリ・課題ラベルの語彙は SKILL.md のシグナル定義表を正とし、この表は参照用の写し（変更時は両方を更新する）。レポートの課題マップ章もこの語彙を使う。

| カテゴリ | 課題ラベル | シグナル | 検知内容（要約） |
|---|---|---|---|
| PR 設計・分割 | `oversized-prs` | S1 | avg_lines_changed_per_pr 前期間比 +30%（両期間 n≥50） |
| PR 設計・分割 | `closed-without-merge` | S11 | prs_merged / prs_created < 70% |
| レビュー滞留 | `individual-review-latency` | S2 | 個人 lead_time_pr_to_review > team×2（n≥20・auto-approve 前提チェックを通過） |
| レビュー滞留 | `repo-review-latency` | S5 | repo p50 lead_time_pr_to_review > 8h（n_reviewed≥20・auto-approve 前提チェックを通過） |
| レビュー滞留 | `approval-to-merge-delay` | S4 | lead_time_approval_to_merge > 24h（merged n≥20） |
| レビュー負荷・偏在 | `review-load-imbalance` | S3 | reviews_created share > 3×(1/アクティブレビュアー数)（5名以上） |
| レビュー負荷・偏在 | `reviewer-overload` | S6 | 個人 avg_time_to_my_review > team×2（team avg ≥5h・個人 reviews_created ≥20） |
| レビュー形骸化 | `unreviewed-merges` | S10 | unreviewed_merge_rate > 30%（> 60% で運用確認） |
| AI 活用 | `ai-usage-drop` | S7 | AI 採用率が期間内で -20pt 以上急落 |
| AI 活用 | `ai-usage-gap` | S8 | 採用率 stddev > 0.3 または 0% メンバー（PR n≥10）2名以上 |
| AI 活用 | `low-ai-usage` | S9 | チーム AI 採用率 < 30%（total_pulls_count > 0 が前提） |

## レコードフォーマット

```markdown
## <課題ラベル>（カテゴリ / 発火シグナル: Sx）

### 提案: <作るものの名前>
- 形態: カスタム Skill | プロンプト | 運用ルール+プロンプト
- ベース・参考にする既存 Skill: <名前>（何を流用するか）。複数ある場合は箇条書きにし、実際のチームで運用されているものは `運用実績:` を先頭に付けて仮説ベースの参照と区別する
- カスタムの要点: <チーム文脈で何を埋め込むか>
- 期待効果: <発火した指標がどう動くはずか — 次回診断で検証できる形で書く>
- 導入手順: <要点 3 行以内>
```

期待効果は**発火シグナルの指標そのもの**で書く。次回診断で同じ指標を見れば提案の効果検証がそのまま閉ループになる。

`出発点にする sample` は任意項目。**配布可能なテンプレート**（`samples/<課題ラベル>.md`）がある課題ラベルにだけ書く。テンプレートはプレースホルダ入りで、そのままでは動かない設計にしてある（チーム文脈を埋め込むことが提案の本体であり、完成品を配ると customization が飛ばされるため）。

**`出発点にする sample` は提案エントリ ID に含めない。** ID の材料は「ベース・参考にする既存 Skill」の先頭項目だけで、sample を足しても ID は変わらない（診断間の比較を壊さないため）。

記述時の注意（提案エントリ ID の決定性に直結する）:

- **「ベース・参考にする既存 Skill」には既存 Skill 名だけを書く。** 素材・資料・チームごとに中身が変わるもの（例: 高採用メンバーの実プロンプト）は「カスタムの要点」に書く。この行は提案エントリ ID の材料になるため、Skill 名でないものが混ざると ID が意味を持たなくなる
- **区切りは `、` を使う。** ` + ` は ID の連結文字なので、区切りなのか名前の一部なのか判別できなくなる
- **「期待効果」に書く閾値は既定値での記述例**。実行時に `thresholds` が上書きされている場合、レポートには**その run で実際に判定に使った閾値**を書く（カタログ文をそのまま転記すると食い違う）

## oversized-prs（PR 設計・分割 / 発火シグナル: S1）

### 提案: リポ構成・revert 単位を焼き込んだタスク分解プロンプト
- 形態: プロンプト（運用が定着したらカスタム Skill 化）
- ベース・参考にする既存 Skill: task-breakdown（1 Task = 1 PR = 1 Revert Unit の分解原則）、feature-breakdown（Issue 分割フロー）
- カスタムの要点: チームのリポジトリ構成・レビュー体制・stacked PR 運用の有無を前提条件として埋め込み、実装着手前に「この Issue を何 PR に分けるか」を出力させる
- 出発点にする sample: `samples/oversized-prs.md`
- 期待効果: avg_lines_changed_per_pr の増加傾向の反転（Δ+30% 発火の解消）
- 導入手順: チームの分割慣行をヒアリングしてプロンプト化 → Issue 着手時の標準ステップに組み込み → 次回診断で S1 を確認

## closed-without-merge（PR 設計・分割 / 発火シグナル: S11）

### 提案: 実装着手前の設計合意プロンプト（プレフライトレビュー）
- 形態: プロンプト + 運用ルール
- ベース・参考にする既存 Skill:
  - feature-breakdown（設計フェーズ部分）、estimate-effort（着手前の設計確認の型）
  - `運用実績:` create-plan / impl-plan（フロントエンドのプロダクトリポジトリの `.claude/commands/`）— 実装計画を GitHub Issue として作成し、その Issue をもとにステップバイステップで実装する2段構成。**着手前の設計合意ゲートが実装され運用されている実例**で、提案するプレフライトレビューの具体形そのもの
- カスタムの要点: AI で PR 作成まで直進する前に、方針サマリ（変更対象・アプローチ・影響範囲）を人間レビュアーに確認する軽量ゲートを挟む。AI 活用下で「レビュー指摘→方針転換→PR 破棄」になるパターンの上流対策
- 期待効果: prs_merged / prs_created の改善（< 70% の解消）
- 導入手順: 方針サマリのテンプレートを作成 → 一定規模以上の Issue で着手前確認を運用ルール化 → 次回診断で S11 を確認

## individual-review-latency（レビュー滞留 / 発火シグナル: S2）

### 提案: チーム固有チェックリスト内蔵のセルフレビュー カスタム Skill
- 形態: カスタム Skill
- ベース・参考にする既存 Skill:
  - self-reviewer（PR 前セルフレビュー）、update-self-review-checklist（過去レビューコメントからのチェックリスト生成）
  - `運用実績:` custom-reviewer（フロントエンドのプロダクトリポジトリ）— 特定レビュアーの過去 PR レビュー履歴から暗黙知を抽出する Analyzer と、その観点で新規 PR をレビューする Reviewer の2段構成。**チーム固有チェックリストの作り方の実装済み実例**
  - `運用実績:` test-quality-evaluator / test-code-writer（フロントエンドのプロダクトリポジトリ）— セルフレビュー時のテスト品質観点。カバレッジ・アサーション品質・記法品質の3軸評価と、テスト実装のベストプラクティス
  - `運用実績:` coding-style / coding-style-locale / coding-style-routes（フロントエンドのプロダクトリポジトリ）— 規約をチェックリスト化する粒度の実例。全体スタイル・多言語・ルーティングのように**領域ごとに分割する単位**が参考になる
- カスタムの要点: 該当メンバーの PR で繰り返される指摘をチェックリスト化して焼き込み、レビュー依頼前に自動セルフレビュー。レビュアーが着手しやすい PR 説明（変更理由・確認観点）の整備も含める
- 出発点にする sample: `samples/individual-review-latency.md`
- 期待効果: 該当メンバーの lead_time_pr_to_review が team avg ×2 未満に低下
- 導入手順: 該当メンバーの直近レビューコメントを収集・チェックリスト化 → セルフレビューを PR 作成フローに組み込み → 次回診断で S2 を確認

## repo-review-latency（レビュー滞留 / 発火シグナル: S5）

### 提案: 対象リポ専用レビュー観点ガイド（PR オープン時自動提示）
- 形態: プロンプト + Actions 運用
- ベース・参考にする既存 Skill: human-review-guide（レビュー観点の自動提示）、setup-human-review-guide（PR オープン時の Actions 化パターン）
- カスタムの要点: 詰まりリポのドメイン知識・レビュー観点を文書化し、PR オープン時に自動提示。特定の詳しい人でなくてもレビューに入れる状態を作る
- 期待効果: 該当リポの p50 lead_time_pr_to_review が 8h 未満に低下
- 導入手順: 該当リポの過去レビューから観点を抽出 → ガイドを Actions で自動投稿 → 次回診断で S5 を確認

## approval-to-merge-delay（レビュー滞留 / 発火シグナル: S4）

### 提案: approve 済み放置 PR の定期棚卸しプロンプト + auto-merge 運用
- 形態: プロンプト + 運用ルール
- ベース・参考にする既存 Skill: merged-pr-summary（定期サマリの実行パターン）
- カスタムの要点: approve 済み・未マージの PR を定期リストアップし、ブロック理由（CI 待ち / デプロイ枠 / コンフリクト / 単純放置）を分類して通知。単純放置が多ければ auto-merge の有効化を運用ルールとして提案
- 期待効果: lead_time_approval_to_merge が 24h 未満に低下
- 導入手順: 棚卸しプロンプトを定期実行に設定 → ブロック理由の分布を確認して運用ルールを決定 → 次回診断で S4 を確認

## review-load-imbalance（レビュー負荷・偏在 / 発火シグナル: S3）

### 提案: 集中レビュアーの観点を形式知化する観点移転プロンプト
- 形態: プロンプト + 運用ルール
- ベース・参考にする既存 Skill: update-self-review-checklist（レビューコメント収集・チェックリスト化のロジック）、human-review-guide
- カスタムの要点: レビューが集中しているメンバーの過去レビューコメントから観点を抽出・ガイド化し、他メンバーがレビューに入れる素地を作る。レビュアーローテーションの運用ルールとセットで導入
- 期待効果: reviews_created の share が 3×(1/アクティブレビュアー数) 未満に分散
- 導入手順: 集中レビュアーの観点を抽出・ガイド化 → ローテーション運用を開始 → 次回診断で S3 を確認

## reviewer-overload（レビュー負荷・偏在 / 発火シグナル: S6）

### 提案: AI 一次レビュー委譲フロー（カスタム レビュー Skill）
- 形態: カスタム Skill
- ベース・参考にする既存 Skill:
  - codex-reviewer（AI レビューの実行パターン）、self-reviewer
  - `運用実績:` custom-reviewer（フロントエンドのプロダクトリポジトリ）— 過負荷レビュアー本人の過去レビュー履歴から観点を抽出して AI に一次レビューさせる構成。**AI 一次レビュー委譲の運用実例**であり、S3（観点の移転）と同じ資産を使い回せる
- カスタムの要点: 機械的指摘（規約・テスト漏れ・タイポ）を AI 一次レビューに委譲し、人間は設計判断に集中する。過負荷メンバーへのレビュー依頼ルーティングの見直しも併せて提案
- 出発点にする sample: `samples/reviewer-overload.md`
- 期待効果: 該当メンバーの avg_time_to_my_review が team avg ×2 未満に低下
- 導入手順: AI 一次レビューをチームのレビューフロー前段に配置 → 人間レビューの対象を設計判断に限定 → 次回診断で S6 を確認

## unreviewed-merges（レビュー形骸化 / 発火シグナル: S10）

### 提案: PR オープン時の AI レビュー自動投稿（Actions + プロンプト）
- 形態: プロンプト + Actions 運用
- ベース・参考にする既存 Skill: setup-human-review-guide（PR オープン時 workflow のパターン）、codex-reviewer
- カスタムの要点: レビューなしマージが常態のリポに、最低限のレビュー観点を自動投稿する。サラッと approve する文化（ペアプロ等）でも観点の担保はできる。> 60% の場合は意図的運用かをまず確認し、意図的ならその旨をチーム合意として明文化する（診断の免責にも反映）
- 期待効果: unreviewed_merge_rate が 30% 未満に低下（または意図的運用の明文化）
- 導入手順: 運用意図の確認 → AI レビュー自動投稿を Actions で導入 → 次回診断で S10 を確認

## ai-usage-drop（AI 活用 / 発火シグナル: S7）

### 提案: 停滞要因ヒアリング→再導入のオンボーディング プロンプト
- 形態: プロンプト
- ベース・参考にする既存 Skill: AI活用プロンプト集（チームで使われている実プロンプトを集約したもの）
- カスタムの要点: 急落時期に重なるイベント（モデル/ツール変更・ライセンス・障害・締切前の駆け込み）をヒアリングし、要因別の再導入プランを提示する
- 期待効果: AI 採用率 Δpt の回復（-20pt 発火の解消）
- 導入手順: 急落時期とイベントの突き合わせ → 要因別プランの実施 → 次回診断で S7 を確認

## ai-usage-gap（AI 活用 / 発火シグナル: S8）

### 提案: 高採用メンバーの使い方を移転するペア活用セッション プロンプト
- 形態: プロンプト + 運用ルール
- ベース・参考にする既存 Skill: AI活用プロンプト集（チームで使われている実プロンプトを集約したもの）
- カスタムの要点: 高採用メンバーの実際の使い方（プロンプト・ワークフロー）を教材化し、低採用メンバーとのペアセッションを設計する。0% メンバーには最初の 1 PR を伴走
- 期待効果: 採用率 stddev ≤ 0.3・0% メンバー（PR n≥10）の解消
- 導入手順: 高採用メンバーの使い方を教材化 → ペアセッションを実施 → 次回診断で S8 を確認

## low-ai-usage（AI 活用 / 発火シグナル: S9）

### 提案: 技術スタック特化の導入スタータープロンプト集
- 形態: プロンプト集
- ベース・参考にする既存 Skill:
  - AI活用プロンプト集（チームで使われている実プロンプトを集約したもの）
  - `運用実績:` generate-feature / generate-presentational-component / generate-graphql-mock（フロントエンドのプロダクトリポジトリの `.claude/commands/`）— フィーチャーライブラリ・コンポーネント・GraphQL モックの雛形生成。**定型作業の自動化をスラッシュコマンド化した実例**で、スタータープロンプト集の粒度の参考になる
  - `運用実績:` recharts（フロントエンドのプロダクトリポジトリ）— チャートライブラリの使い方を skill 化したもの。**ライブラリ特化ナレッジを skill にする実例**（毎回同じ調べ物をしている領域を1つ選ぶ、という選定の型）
- カスタムの要点: チームの言語・フレームワーク・定型作業（テスト作成・レビュー・リファクタ等）に合わせた「最初の一歩」プロンプト集を配布する
- 期待効果: チーム AI 採用率が 30% 以上に上昇
- 導入手順: チームの定型作業を棚卸し → スタータープロンプト集を配布・共有会を実施 → 次回診断で S9 を確認

## 将来候補（v2 シグナル候補と対応提案の置き場）

v1 では診断しない。シグナル追加時にこのセクションから本編へ昇格させる。

- **p90/p50 テール比**（PR 滞留の定量化）: 発火時の提案候補は滞留 PR の定期棚卸し（approval-to-merge-delay の提案を一般化）
- **レビューコメント数系**（レビュー形骸化の深掘り）: unreviewed-merges の提案と統合予定
- **個人単位の AI 利用推移**: チーム月次の ai-usage-drop では、特定メンバーが途中で AI 利用を停止しても検知できない（本番実行で実例を確認）。メンバー別 AI 利用レポートの `daily[]` から個人の推移を構成すれば検知可能。発火時の提案候補は ai-usage-drop の提案を個人単位に適用したもの
- **ドメイン調査・ドキュメント生成系の横断ベース**: `運用実績:` tool-integration-research / comment-document（バックエンドのプロダクトリポジトリの `.claude/skills/`）。前者は新規外部ツール連携の着手前調査をドキュメント化する型、後者はクラス種別ごとのコメント規約を skill 化した型。現行 11 シグナルに直接対応する課題ラベルは無いが、「調査・ドキュメント整備の属人化」を扱うシグナルを追加した際のベース候補
- **`get_ai_tool_impact_report`（AI ツール別のサイクルタイム内訳。2026-08 リリース済み。診断コアはレポート 6 章の参考情報として取得済み）を使ったシグナル判定への昇格**: S7〜S9 発火時の原因分解（全体離脱か特定ツール停止か）、リードタイム章と AI 章の接続（closed-without-merge の背景仮説の裏付け）、ツール軸の提案が可能になる
