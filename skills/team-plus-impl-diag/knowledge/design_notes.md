# 設計根拠と実測の来歴

SKILL.md の判定規則がなぜその形になっているかを記録する。**診断の実行時には読まない。** 閾値や判定方式を見直すとき、および「なぜこの条件なのか」を確認するときだけ参照する。

判定に必要な規則そのものは SKILL.md 側にある。ここにあるのは根拠と、再校正の際に踏まえるべき前提だけ。

## auto-approve 前提チェックで team avg を使わない理由

チーム全体の p50 lead_time_pr_to_review のみで判定し、team avg での代用も OR 条件の追加もしない。

リードタイムの分布は右に裾を引くため、avg ≥ p50 がほぼ常に成立する。avg 条件を使うと「レビューは実際に行われているが平均が小さいだけの速いチーム」を誤って判定対象外にする（偽陰性）。実測 7 チームでも、avg 条件が単独で結論を決めたケースは無かった。

## bot 検知で Team+ の bot フラグを使わない理由

Team+ の member が持つ bot フラグ（bool）は使わず、行動パターンから判定する。

実データで、PR を量産している bot アカウントが `bot: false` になっている例を確認している。フラグを信じると検知漏れが起きるため、PR とレビューの比率・レビュー着手時間・日次件数の分散という行動側の特徴を根拠にしている。

## bot 検知 ③ の CV 閾値 0.25 の由来

実測では bot の CV が 0.158、人間が 0.359〜1.037 に分布しており、その間を取って 0.25 を暫定値とした。

ただし **CV 0.53 の bot の実例**があり、CV 単独では分離できないケースがある。このため ③ は単独条件としつつ、④（PR 量産型）⑤（名前パターン）の補助 2 条件による検知と併用する設計になっている。

**再校正時の注意**: 上記の実測値は、`daily[]` に `total_pulls_count` が無かった時期の `ai_pulls_count` ベースの計測に由来する。現在の規定は total ベースで、AI 率が低いメンバーでも母数が確保でき判定不能は減る一方、CV の値そのものは変わりうる。閾値を見直すのは total ベースの実測が十分に蓄積してから行う。

## サーベイ系ツールの実測（体感の裏付けレイヤーの前提）

体感の裏付けレイヤー（定量シグナル × サーベイの 4 象限）の判定規定は、以下の実測（2026-09-15・1 組織）に基づく。

**集計除外と配信ゼロの見え方**:

- 回答 2 件未満で集計除外された配信は、レスポンスから**エントリごと消える**（null や 0 ではない）。「配信はあったが除外」と「配信が無い」は外形上区別できないため、規定は「窓内に集計済み配信が無い」の一本にまとめるしかない
- 「サーベイ未設定 / 閲覧権限なし」は別形態で、monitoring の解決後に**エラー**（「resource not configured / no permission」）が返る（サーベイが紐付いていない複数の monitoring で再現を確認）。「設定あり・配信なし」（`transitions: []`・stats 両値 null）とは機械的に区別できるが、未設定と権限なしはこの同一エラーで外形上区別できない。エラー時も診断本体は止めず「サーベイ未実施」扱いにできる

**前回差分（previous_*_score_difference）**:

- スコアと同じ 5 点スケールの差分・0.1 刻み。**史上初回の配信のみ null**（実測で確認）。2 回目以降は差分ゼロでも `0` が返るため、null と 0 の意味が異なる
- 比較対象は「その配信の直前の配信」で、**要求した期間の外の配信も参照される**。窓の切り方に依存せず前回差分が取れるため、クライアント側で窓外の配信を取り直す必要は無い

**配信の特定と周期**:

- 期間指定は deadline ベースで API がフィルタする。`transitions` の各エントリは `date`（= deadline_date）を持ち**昇順**で返るため、最新配信は配列末尾で決定的に取れる
- **配信周期は組織設定で可変**（実測した組織では月次 → 四半期に変更されていた）。90 日窓に入る配信は 0〜3 件になりうる。「最新配信のみで判定」の規定はこの可変性を吸収するためにある

**カテゴリスコアの精度とタイ**:

- `s/p/a/c/e_score` は小数第 1 位までの 1 桁精度。**同率タイは現実的に起こる**（実測でも 0.1 差の僅差カテゴリがあった）。最低カテゴリの「タイ全採用」規定はこの精度を前提にしている
- 設問とカテゴリの対応は `get_survey_question_stats` の `category` フィールドで機械的に引ける（必須設問 15 問・文言は API 側で解決済み）

**自由記述（f_1 / f_2）**:

- `answers` は匿名の配列で回答者情報を含まない。「回答 2 件未満の配信を除外する」下限は**配信単位の完了回答数**に掛かるガードであり自由記述にも適用されるが、集計対象の配信でも自由記述は任意回答のため**設問単位では回答 1 件だけが返りうる**（実測で確認。完了回答が複数ある配信で f_2 の回答が 1 件だった）。原文がそのまま返る自由記述で回答が 1 件のとき、書き手の特定リスクは数値集計より高く、「レポートには原文・要約とも出さない」の根拠になっている

**実測できていないこと（再校正時の注意）**:

- カスタム設問のレスポンス形（`custom_question_text` の解決）は未実測。**カスタム設問対応をスコープに入れる際は、先にカスタム設問を運用している組織で実測し、来歴をここに追記すること**（現行の必須設問のみのスコープでは判定に影響しない）
- 回答受付中の配信は `end_date = 今日` のときのみ暫定値で含まれる仕様（tool description 記載・実測機会なし）。impl-diag の終端は「実行日 - 2 日」のため確定値のみを扱うことになり、この仕様には依存しない

## 既存 skill の確認を名前だけ・直下 1 階層までにしている理由

Skills 提案の前に、チームがすでに持っている skill・コマンド・エージェントの名前を一覧し、提案と役割が重なるものを「既存の類似 skill」として示す。同じ役割の skill がすでにあるチームに「新しく作る」提案を出すと、skill の重複を診断が増やしてしまうため。

**名前だけで判定し、提案は消さない**:

- 中身を読んでの判定は現時点では行わない。読み取り量が件数に比例して増えるため（実測 2026-10-01・1 環境: リポジトリを並べた親ディレクトリで、skill 等を持つ `.claude` が 14 箇所・名前は 147 件）
- 名前だけの判定は外れうる（役割が違うのに名前が似ている・同じ役割なのに名前から読み取れない）。このため類似があっても提案は落とさず列で示し、導入手順の書き出しにも「中身を確認し、同じ役割なら」を入れて、誤一致のときに無関係な skill の拡張へ誘導しないようにしている
- 提案エントリ ID と提案の集合に一覧を影響させないのは、実行する場所によって ID 集合が変わると診断間の比較が成立しなくなるため（サーベイ自由記述 f_2 と同じ扱い）

**探す場所を「実行ディレクトリと直下 1 階層」にしている**:

- 想定している実行場所は「チームのリポジトリ」と「リポジトリを並べた親ディレクトリ」の 2 つ。上記の実測では、skill 等を持つ `.claude` はすべて直下 1 階層にあった
- 深さを無制限にしないのは、依存パッケージや worktree の複製まで歩くことになり、時間がかかるうえ同じ skill が重複して一覧に載るため
- ディレクトリ構成は利用者ごとに異なるが、**構成を推測して探す範囲を広げることはしない**。推測は外れたときに気づけない（0 件のまま「新しく作る」提案が出る）。代わりに `existing_skill_roots` で場所を指定できるようにし、探した範囲と件数をレポートに必ず出して、拾えていないことに読み手が気づけるようにしている
- `~/.claude`・プラグイン・チームモニタリングの対象リポジトリをリモート経由で見ることは対象外。リモート経由は認証とリポジトリ数ぶんの呼び出しが要る

**再校正時の注意**:

- 類似の判定基準は未校正。誤一致や見逃しが多い場合は、カタログの各エントリに「類似名の手がかり」となる語を持たせて判定を安定させる案がある（語の保守が増え、`review` のような一般的な語は誤一致も増やすため、実運用で揺れが問題になってから検討する）
- 他チームのリポジトリにある skill も一覧に入る。候補が多い環境で誤一致が目立つ場合は、チームモニタリングの対象リポジトリと同名のディレクトリに絞る案がある（リポジトリ一覧を取得しない scope で呼び出しが 1 回増え、clone 先のディレクトリ名がリポジトリ名と異なると拾えない）
- リポジトリのサブディレクトリから実行した場合に上位の `.claude` を自動で見る案は、どこまで遡るかの規定が増えるため見送っている（`existing_skill_roots` で代替できる）

## 閾値全般の位置づけ

シグナル定義表の閾値はいずれも複数組織の実データ探索に基づく暫定値で、実行時に thresholds で上書きできる。閾値の境界付近で判定が決まった場合にレポートへ注記させているのは、暫定値であることを診断の読み手に伝えるため。

- percentile（p50 / p90）はサーバ側算出で、補間の有無が公開されていない。境界 ±10% に収まる判定は注記する
- bot 検知 ③ の CV は境界 ±0.1 に収まる判定を注記する
