# team-plus-impl-diag

チームの実装〜マージプロセス（コミット〜マージ）を Team+ MCP のデータで診断し、課題マップと改善 Skills 提案を含む Markdown レポートを出力する。

## 使いどき

「実装プロセスを診断して」「マージプロセスを診断して」「impl-diag」などで起動する。診断の対象は**コミットからマージまでの実装フェーズ**に限られる。企画・設計フェーズや、開発資本スコアのような組織全体の指標を起点にした診断は本 skill の対象外。

- `impl-diag` — memory の monitoring を既定期間で診断する
- 「<チーム名> の実装プロセスを診断して」
- 「<チーム名> を scope=repos で診断して」 — リポジトリ別のレビュー滞留に絞る（API 呼び出しを削減できる）

## 入力

| 引数 | 必須 | 既定 | 説明 |
|---|---|---|---|
| monitoring_name | ○（データ解決順で補完可） | - | 診断対象の monitoring 名（fuzzy 検索可） |
| period | - | quarter（直近 90 日） | 診断期間。**`quarter` のみ受け付ける**（下記「期間の定義」） |
| start_date | - | -（終端から逆算） | 期間開始日 YYYY-MM-DD |
| scope | - | all | all / monitorings / repos / members |
| thresholds | - | コア定義の既定値 | シグナル閾値の上書き（キーは config/defaults.yml 参照） |

## データ解決順

1. 実行時の引数・ユーザー指示
2. 個人 memory: `~/.claude/team-plus-impl-diag/memory.yml`（存在すれば。defaults.yml と同一スキーマ）
3. skill 同梱の `config/defaults.yml`
4. いずれにも無い必須項目はユーザーに確認する

## 参照ファイル

- `knowledge/skill_catalog.md`: 提案の元になる知識（「Skills 提案の生成」の工程で読み込む）
- `samples/<課題ラベル>.md`: 提案の出発点にする配布可能なテンプレート（プレースホルダ入り）。**診断の実行時には読まない**。カタログの `出発点にする sample` が指すパスを導入手順に載せるだけでよい
- `config/defaults.yml`: 既定値とスキーマ定義
- `knowledge/design_notes.md`: 閾値・判定方式の設計根拠と実測の来歴。**診断の実行時には読まない**（閾値や判定方式を見直すときだけ参照する）

## 実行手順

1. データ解決順に従って入力を確定する
2. 以下の「診断コア」を順に実行する
3. レポートを Markdown で出力する（保存先の指定があればファイルに保存）

工程の区切り（データ取得の完了 / シグナル判定の完了 / 提案生成の完了）で 1 行ずつ進捗を報告する。リポ数・メンバー数によっては MCP 呼び出しが数十回に達し、無言の時間が長くなるため。データ取得の着手時には「リポ N 件 × 2 回 + メンバー M 名（P ページ）」のように**これから行う呼び出し数の見込み**を添える。

## 診断コア

### スコープと必須ルール

- 計測範囲は開発プロセスの実装フェーズ「コミット〜マージ」。指標は Team+ MCP が提供する範囲に限定する
- アウトプットは診断レポートと Skills 提案まで。提案された Skill の実装は利用者判断（本診断のスコープ外）
- **数値・指標は必ず Team+ MCP で取得する**。PR タイトルの文字列マッチ等、Team+ MCP 以外のデータソースからの代替推定は使用しない
  - Team+ MCP のレスポンスをクライアント側で再集計すること（AI 利用レポート `daily[]` の期間合算・メンバー別集約等）は、データソースが Team+ MCP のみであるため代替推定に当たらず、このルールの範囲内である
- monitoring 名・メンバー名は fuzzy 検索で解決する（MCP サーバー側に実装済み。候補が複数提示された場合はユーザーに確認する）
- Team+ のデータは集計遅延があり直近2日分は取得できない。期間の終端は「実行日 - 2日」とする

### 期間の定義

**stats 系（#2 #4 #6）の窓は開始日でしか指定できない**。`start_date` は必須パラメータで、窓は `start_date` から `range` の長さ分（`quarter` なら 90 日）。終端を渡すパラメータは無いため、当期・前期とも「開始日」を計算して渡す。`range` の選択肢は day（1日）/ week（7日）/ month（30日）/ quarter（90日）/ end_of_month（start_date からその月の末日まで）。

- **period は `quarter`（90 日）のみ受け付ける**。他の値が指定された場合は診断を始めず、理由を説明してユーザーに確認する。シグナルのガード（prs_created ≥ 50 / 20、n_reviewed ≥ 20 等）は 90 日相当の母数で校正されており、30 日窓ではほぼ全シグナルが母数不足で判定不能になる。加えて AI 利用レポートの最小 period は one_month で、暦月加算では 2 月をまたぐ 30 日窓を包含できず S7 / S9 / S12 の窓が作れない。**期間をずらしたい場合は period ではなく `start_date` を使う**
- 当期（cur）: 終端 = 実行日 - 2日、開始 = 終端 - 89日（`range=quarter` は暦の3ヶ月ではなく **90 日固定**。開始日を含めて 90 日になるよう終端から 89 日引く）
- 前期（prev）: 当期の直前・同じ長さの期間（開始 = 当期開始 - 90日、終端 = 当期開始 - 1日）。Δ系シグナル（S1）の比較に使う。#2 の prev はこの開始日を `start_date` に渡して `range=quarter` で呼ぶ（実測: `start_date=2026-03-04` + `range=quarter` → `2026-03-04..2026-06-01`）
- `start_date` 引数が指定された場合: それを当期開始として扱い、当期終端 = 当期開始 + 89日、前期は上記の定義で当期開始から逆算する。当期終端が「実行日 - 2日」より後になる指定はデータが揃わないため受け付けず、ユーザーに確認する
- 月次推移: 直近 6 つの**完結した暦月**（#3 のバケット。実行中の月・末日が「実行日 - 2日」より後の月は API が返さない）。当期（90 日）とは範囲が一致しないため、レポートには両方の期間を明記する。**シグナル判定に使うのは直近 3 バケットのみ**で、それより前のバケットはトレンド分類（下記「発火シグナルの根拠強化」）の文脈に使う
- **月次アンカー**: 末日が「実行日 - 2日」以下である最新の暦月（= 最新完結月）の、**5 ヶ月前の月初**。実行日だけから機械的に決まり、他のツールのレスポンスに依存しない。#3 の `start_month` と #7 2 回目の `start_date` の両方に渡すことで、月次推移と月次 AI 率のバケットを一致させる（実測 2026-09-01 時点: 実行日 - 2日 = 08-30 → 最新完結月 = 7月 → アンカー = 2026-02-01。#3 は 2026-02〜2026-07 を返し、#7 の窓は 2026-02-01..2026-07-31 で一致）
- AI 利用レポート（get_*_ai_usage_stats）の窓: `start_date` を渡すと `start_date` から period 分（暦月加算）- 1日まで。省略すると**終端 = 実行日 - 2日**から period 分さかのぼる（この既定窓は暦月境界に揃わない）。窓の終端が「実行日 - 2日」より後になる指定は API がエラーを返す。`period` の選択肢は one_month / two_months / three_months / six_months。stats 系の当期（90 日固定）と完全一致する窓は指定できないが、three_months の窓は必ず 90 日以上になるため当期を包含する。当期の AI 率は `daily[]` を当期の日付範囲でクライアント合算して算出する

### データ取得手順

| # | ツール | 呼び出し | 依存 | 用途 |
|---|---|---|---|---|
| 1 | get_monitorings | 1回 | - | monitoring_name の解決（fuzzy） |
| 2 | get_team_stats | cur / prev の2回（`start_date`=各期の開始日・range=quarter） | #1 | S1 S4 S10 S11 と、S2 S3 S6 の team 側の値、auto-approve 前提チェックの全体 p50 |
| 3 | get_team_stat_transitions | 1回（months=6・`start_month`=月次アンカーの月） | #1 | 月次推移章（直近 6 完結暦月）とトレンド分類 |
| 4 | get_team_member_stats | cur 1回（`start_date`=当期開始・range=quarter） | #1 | S2 S3 S6 のメンバー別の値 |
| 5 | get_team_repositories | 1回 | #1 | リポ一覧（repo_id）。#6 とリポジトリ別ドリルダウンの呼び出し単位になる |
| 6 | get_team_stats | リポごとに2回（cur・`start_date`=当期開始・`repository_ids`=[そのリポ]。percentile_rank 省略= p50 と percentile_rank=90） | #5 | S5（リポ別 p50 / p90 / n_reviewed）と、リポジトリ別ドリルダウンの cur 側 |
| 7 | get_team_ai_usage_stats | 2回（start_date 省略・period=three_months と、月次アンカー指定・period=six_months） | #1 | S7 S9 |
| 8 | get_team_member_ai_usage_stats | ページ数分（period=three_months） | #1 | S8 S12 と bot 検知 ③ |
| 9 | get_ai_tool_impact_report | 1回（start_date=当期開始・end_date=当期終端） | #1 | AI 活用章の AI ツール別サイクルタイム（参考情報） |

- **並列実行**: #1 の完了後、#2〜#5・#7・#8・#9 は相互に独立しており並列に呼んでよい。#6 は #5 の repo_id 一覧を待つが、リポ単位では並列可。順序に意味があるのは「#1 → その他」と「#5 → #6」の 2 つだけで、それ以外を直列に実行する理由は無い
- 取得する stat types（#2〜4）: `prs_created` `prs_merged` `avg_lines_changed_per_pr` `lead_time_pr_to_review` `lead_time_approval_to_merge` `lead_time_to_merge` `avg_time_to_my_review` `reviews_created` `unreviewed_merge_rate`（メンバー側は S2 S3 S6 とガード判定に使う分のみ）。#2 の cur には `percentile_lead_time_pr_to_review` と `lead_time_pr_to_review_sample_size` も加える（percentile_rank 省略 = p50。auto-approve 前提チェックに使う）
- **scope 指定時はデータ取得も絞る**: 対象章に必要なツール呼び出しのみ行い（monitorings → #1〜3 / repos → #1・2・5・6 / members → #1・2・4・7・8・9）、取得しなかったデータに依存するシグナルは診断サマリに「scope 対象外」と明記する
- **リポ別 p50 / p90（#6）**: percentile 系 stat は 1 リクエストにつき 1 つの順位しか返さないため、リポごとに p50 と p90 の 2 回呼ぶ。`lead_time_pr_to_review_sample_size` は p50 側の呼び出しに同梱し、S5 のガード（n_reviewed ≥ 20）に使う。p50 側で sample_size = 0 のリポは p90 の呼び出しを省略してよい。**sample_size = 0 のとき percentile 系 stat は `null` で返る**（実測）。`null` は「レビュー済み PR が無く算出不能」であり `0`（算出できて 0 時間）とは意味が異なるため、リポジトリ別章では `-` と表記して 0 と区別する
- **ドリルダウン用の stat は #6 に同梱する**: p50 側の `stats` に `avg_lines_changed_per_pr` `prs_created` `unreviewed_merge_rate` `prs_merged` も加える。1 リクエストで複数 stat を返せるため追加の呼び出しは発生せず、S1 / S10 発火時のリポジトリ別ドリルダウン（下記）に必要なリポ別の cur 値がこれで揃う。**発火時に取り直すのは S1 の prev 側（リポごとに 1 回）だけ**になる
- **percentile はサーバ側算出**: p50 / p90 は Team+ API の percentile 系 stat（`percentile_lead_time_pr_to_review` 等）をそのまま使い、クライアント側では算出しない。サーバの算出方法（補間の有無）は公開されていないため、閾値の境界 ±10% に収まる値で判定が決まった場合はその旨をレポートに注記する
- **母集合の違いに注意**: AI 利用レポートの total_pulls_count は、stats の prs_created と母集団が異なる（PR 作成者だけでなくコミット contributor にも計上されるため同じ人でも prs_created より大きく出る。実測で個人単位 約 1.5 倍）。互いの数値を直接比較せず、比較した場合は注記する
- **`unreviewed_merge_rate` は % 表記**（0〜100・小数第1位まで）。`0.1` は 0.1% であり比率ではない。S10 の閾値（30 / 60）とはそのまま比較する
- **AI 利用レポート（#7 #8）は既に monitoring スコープ**: get_team_ai_usage_stats / get_team_member_ai_usage_stats は `repository_ids` を指定しなくても monitoring の対象リポジトリに絞られる（未指定時は monitoring の全リポにフォールバックする）。**特定リポにさらに絞りたい場合だけ** get_team_repositories の `repo_id` を渡す。その場合は片側だけ絞ると S7 / S9 の比較が壊れるため、team 側（#7）とメンバー側（#8）に同じ ID を渡す
- **メンバー別 total_pulls_count は合算しない**: メンバー別値は PR 作成者だけでなくコミット contributor にも紐づくため、1 つの PR が複数メンバーに計上される。メンバー合計はチーム値（#7）を必ず上回り（実測 1.1〜2.0 倍）、比率としての意味を持たない。S8 は個人ごとの AI 率（ai ÷ total）だけを使い、チーム値との合算・突き合わせはしない
- **当期 AI 率と月次 AI 率（#7）**: 1 回目は start_date 省略・period=three_months で呼び、`daily[]`（date / total_pulls_count / ai_pulls_count）を当期の日付範囲でクライアント合算して当期のチーム AI 率（S9）を出す（窓が当期より数日広いため total_* をそのまま使わない）。2 回目は**月次アンカー**（上記「期間の定義」。最新完結月の 5 ヶ月前の月初）を start_date に渡して period=six_months で呼び、`daily[]` を暦月で合算して月次 AI 率を 6 バケット出す（S7 の判定は直近 3 バケットの隣接比のみ。それ以前はトレンド分類の文脈）。アンカーは実行日だけから決まり #3 のレスポンスに依存しないため、#3 を呼ばない `scope=members` でも算出でき、#3 を呼ぶ scope では月次推移とバケットが完全に一致する。six_months の daily[] は約 180 日分あるので、合算はスクリプトで行い日次の生データをレポートに展開しない。daily[] は急落時期の特定の補助にも使う
- **個人の月次 AI 率（S12・#8）**: #8 の各メンバーの `daily[]` を暦月で合算する。窓（start_date 省略・three_months）を暦月で割り、**先頭のバケットは不完全な場合にのみ捨てる**。無条件に捨ててはいけない: 「実行日 - 2日」が月末日にあたる日（実行日 = 月末日 + 2日。月に 1 日発生する）は窓の先頭が月初に揃って**完結月になる**ため、捨てると比較可能な隣接ペアが 2 組から 1 組に減り、しかもエラーにならず正常なレポートに見える（実測 2026-09-01: 実行日 - 2日 = 08-30 → 窓は `2026-05-31..2026-08-30` で先頭 5 月は 1 日のみ＝不完全。実行日が 09-02 なら窓は `2026-06-01..2026-08-31` で先頭 6 月は完結）。末尾のバケットは不完全な場合も対象日数をレポートに注記した上で使う（実行日が月初のときは末尾が前月になるため、「実行月」と決めつけない）。このためバケットはチーム月次（S7。完結暦月のみ）と末尾 1 つズレうる — S12 の根拠にバケットの対象期間を必ず明記する。判定は直近 3 バケットの隣接比較に限定し、**バケットが 3 つ未満のメンバーは判定不能**として「取れていない情報」章に回す
- **メンバー別 AI 利用データ（#8）は必ずページングする**: メンバーごとに period 日数分の `daily[]` が付くため、レスポンスは「メンバー数 × 日数」で膨らむ。**1 回の呼び出しが「per_page × period 日数 ≤ 300」に収まるよう per_page を決める**（three_months = 約 92 日なら per_page ≤ 3、six_months = 約 180 日なら per_page ≤ 1）。実測で 7 名 × 92 日 = 644 エントリ（77,000 文字）がツール出力の上限を超え、レスポンス全体が読めなくなった。1 回で全メンバーを取れるからといって per_page を既定（100）のままにしない
- **分担の閾値はページングとは別**: メンバー数 × 日数が目安 1,000 を超える場合は下記「メンバー別 AI 利用データ収集のサブエージェント分担」に従う。これは**メインのコンテキスト量**の話で、上記のページングは**1 レスポンスの上限**の話。1,000 以下でもページングは必須である（`pagination` の total_pages / per_page を読み、per_page は API 側で下げられることがあるため実際に適用された値を確認する）
- AI 率 = total_ai_pulls_count ÷ total_pulls_count（0 除算に注意。分母 0 は「判定不能」）。**内部では 0〜1 の比として扱う**（S8 の閾値 s8_stddev = 0.3 はこのスケール）。S7 / S9 / S12 の閾値は pt / % 表記なので、比較時に ×100 して揃える。レポートへの表示も % に統一する

### メンバー別 AI 利用データ収集のサブエージェント分担

get_team_member_ai_usage_stats（#8）はメンバーごとに period 日数分の `daily[]` を返すため、メンバー数 × 日数が大きい monitoring（目安 1,000 超。例: 12 名 × 92 日）ではレスポンスがメインコンテキストを圧迫する。以下の分担で実行する。

- **分担の要否判定**: #8 を `per_page=1` で 1 ページ目だけ呼び、`pagination` からメンバー数を読む。メンバー数 × period 日数が目安 1,000 を超えたら分担する。この判定に #4 のメンバー数は使わない（#4 を取得しない scope があり、依存を増やすため）
- 収集用サブエージェントにページを割り当てて実行し、`daily[]` の生データをメインに返させない。メインに返すのは**メンバーごとの集約値のみ**: node_id / name / total_ai_pulls_count / total_pulls_count / 平日稼働日数（下記 bot 検知 ③ の母数）/ 平日稼働日の total_pulls_count の変動係数 / 暦月別の total_pulls_count と ai_pulls_count（S12 用）
- **サブエージェントへの指示は自己完結させる**: サブエージェントは SKILL.md を読んでいないため、別節への参照ではなく**規定の本文を prompt に埋め込む**。埋め込むのは ① 呼び出しパラメータ（monitoring_name / period / 担当ページ番号 / per_page）② 変動係数の算出規定（下記 bot 検知 ③ の全文。母数の定義・下限 20 日・母集団標準偏差）③ 暦月別集計の規定（上記「個人の月次 AI 率」の全文。先頭の不完全暦月を捨てる等）④ 上記の返却項目と出力フォーマット。参照渡しにすると母集団/標本標準偏差・祝日・不完全月の扱いがページごとに揺れ、「再現性の担保単位」の主判定が一致しなくなる
- **S8 / S12 の判定と bot 検知はメイン側で集約値から行う**。サブエージェントは集計のみを担当し、閾値判定はしない（判定を分散させると thresholds の上書きが効かなくなる）
- 複数チームを同時に診断する場合はチーム単位に並列化する
- **中断耐性**: ページごとの集約値は作業用ファイルに書き出し、メインのコンテキストだけに保持しない（セッションの再開や要約で失われると再開できないため）。収集が中断してもページ単位で再開でき、取得済みページの集約値はそのまま再利用して未取得ページのみを取り直す。打ち切った場合は未取得メンバー数をレポートに注記する

### シグナル定義（v2: 12個）

閾値は複数組織の実データ探索に基づく暫定値。thresholds で上書き可能（括弧内はキー名）。v2 で S12 を追加した（それ以外のシグナルの定義・閾値は v1 から不変）。

| ID | 課題ラベル | カテゴリ | 定義・閾値 | 判定ガード |
|---|---|---|---|---|
| S1 | oversized-prs | PR 設計・分割 | avg_lines_changed_per_pr が前期比 +30% 以上（s1_lines_delta_pct） | 両期間とも prs_created ≥ 50。発火時は外れ値 PR の可能性を必ず注記。プロバイダ間の絶対値比較はしない |
| S2 | individual-review-latency | レビュー滞留 | 個人 lead_time_pr_to_review > team avg × 2（s2_team_ratio） | 個人 prs_created ≥ 20。auto-approve 前提チェック（下記）。レポートは **team avg に対する倍率の降順で上位 3 名まで** |
| S3 | review-load-imbalance | レビュー負荷・偏在 | 個人の reviews_created share > 3 × (1 ÷ アクティブレビュアー数)（s3_share_factor） | アクティブレビュアー（reviews_created > 0）が5名以上。人数・share とも **bot 除外後**の母数で数える |
| S4 | approval-to-merge-delay | レビュー滞留 | lead_time_approval_to_merge > 24h（s4_hours） | prs_merged ≥ 20 |
| S5 | repo-review-latency | レビュー滞留 | リポ別 p50 lead_time_pr_to_review > 8h（s5_p50_hours） | リポのレビュー済み PR 数（lead_time_pr_to_review_sample_size）≥ 20。auto-approve 前提チェック（下記） |
| S6 | reviewer-overload | レビュー負荷・偏在 | 個人 avg_time_to_my_review > team avg × 2（s6_team_ratio） | team avg ≥ 5h **かつ 個人 reviews_created ≥ 20**。個人値 > 72h は放置されたレビュー依頼の可能性を注記 |
| S7 | ai-usage-drop | AI 活用 | 月次 AI 率が隣接月比 -20pt 以上低下（s7_drop_pt）。判定は直近 3 バケットの隣接比のみ | AI 系共通前提（下記） |
| S8 | ai-usage-gap | AI 活用 | 個人 AI 率の stddev > 0.3（s8_stddev）、または 0% メンバーが2名以上 | 0% 判定は total_pulls_count ≥ 10 のメンバーのみ。stddev・0% メンバー数とも **bot 除外後**の母数で算出。AI 系共通前提 |
| S9 | low-ai-usage | AI 活用 | チーム AI 率 < 30%（s9_rate_pct） | AI 系共通前提 |
| S10 | unreviewed-merges | レビュー形骸化 | unreviewed_merge_rate > 30% で注意（s10_warn_rate_pct）、> 60% でプロセス不全か意図的運用かの確認を促す（s10_check_rate_pct） | - |
| S11 | closed-without-merge | PR 設計・分割 | prs_merged ÷ prs_created < 70%（s11_merge_rate_pct） | - |
| S12 | individual-ai-drop | AI 活用 | 個人の月次 AI 率が隣接月比 -30pt 以上低下（s12_drop_pt）。月次の算出は「個人の月次 AI 率（S12・#8）」の規定に従い、判定は直近 3 バケットの隣接比のみ | 比較する両月とも個人 total_pulls_count ≥ 10（s12_min_monthly_pulls）。**bot 除外後**。AI 系共通前提（下記）。チーム率が高くても個人の離脱は起きるため S7 と独立に判定する。レポートは急落幅の大きい順に上位3名まで |

**S8 の stddev の算出**（bot 検知 ③ の CV と同じく、規定しないと run 間で値が食い違うため厳密に定める）:

- 対象は #8 の各メンバーの個人 AI 率 = total_ai_pulls_count ÷ total_pulls_count（**0〜1 のスケール**。閾値 s8_stddev = 0.3 もこのスケールで比較する）
- 母集団は **bot 除外後**かつ `total_pulls_count ≥ 10` のメンバー（S8 の「0% メンバー」の数え方と同じ母集団を使う）。分母が 1〜2 件のメンバーの 0% / 100% が stddev を大きく振らせるため、下限を揃える
- `total_pulls_count = 0` のメンバーは AI 率が定義できないため母集団から除く
- 母集団が 3 名未満のときは S8 を**判定不能**とし、「取れていない情報」章に回す
- stddev = **母集団標準偏差（n で割る）**。標本標準偏差（n−1）は使わない（③ と揃える）

### 共通ガード（全シグナル）

- 全指標ゼロの monitoring は診断をスキップし、免責を注記する
- bot / 非人間アカウントは下記「bot 検知と除外」に従って検知し、メンバー別シグナル（S2 / S3 / S6 / S8 / S12）の母数から除外する
- 新設チーム等で prev 期間のデータが無い場合、Δ系（S1）は判定せず「取れていない情報」に分類する
- **AI 系共通前提（S7〜S9・S12）**: チームの total_pulls_count > 0 を判定の前提とする。満たさない場合は「0%」ではなく「判定不能」と診断する
- **auto-approve 前提チェック**: レビューリードタイム系（S2 / S5）は「レビューが実質行われている」ことを前提とする。チーム全体の p50 lead_time_pr_to_review（#2 cur の `percentile_lead_time_pr_to_review`）< 0.5h（auto_approve_p50_hours）**のみで判定する**。該当する場合は S2 / S5 を判定せず、auto-approve / bot レビュー文化の可能性をレポートに注記する
  - p50 は #2 で取得するため、どの scope でもこのチェックを同じ基準で行える
  - team avg での代用・OR 条件の追加はしない（偽陰性になる理由は `knowledge/design_notes.md`）

### bot 検知と除外

メンバー別データ（#4・#8）の取得後に判定する。条件は**単独条件**（①〜③。1 つ成立で bot とみなす）と**補助条件**（④ ⑤。単独では除外せず、2 つ揃った場合にのみ bot とみなす）に分かれる。

**Team+ の member が持つ bot フラグ（bool）は使わない。** 行動パターン（PR とレビューの比率・レビュー着手時間・日次件数の分散）から判定する（フラグを使わない根拠は `knowledge/design_notes.md`）。

| # | 型 | 区分 | 条件 |
|---|---|---|---|
| ① | レビュー専業型 | 単独 | prs_created = 0 かつ reviews_created ≥ 20（bot_reviews_min） |
| ② | 機械的即レビュー型 | 単独 | avg_time_to_my_review < 0.5h（bot_review_time_hours）かつ reviews_created ≥ 20（bot_reviews_min） |
| ③ | 日次件数一定型 | 単独 | メンバー別 AI 利用データ `daily[]` の平日稼働日の変動係数 < 0.25（bot_daily_cv_max）。算出方法は下記 |
| ④ | PR 量産型 | 補助 | prs_created が稼働メンバー（prs_created > 0）の中央値の 2 倍超（bot_prs_median_factor）。中央値は**判定対象本人を含む**稼働メンバー全員から取り、偶数人数のときは中央 2 値の**平均**とする |
| ⑤ | 名前パターン | 補助 | 表示名に `bot` / `agent` / `approve` / `claude` / `copilot` / `devin` / `現場猫` 等を含む。組織ごとに命名が異なる |

**③ の変動係数（CV）の算出**（規定しないと run 間で値が食い違うため厳密に定める）:

- 対象は get_team_member_ai_usage_stats（#8・period=three_months）の `daily[]` の `total_pulls_count`（AI 以外も含む全 PR の日次件数）
- 母数は**平日（月〜金）かつ `total_pulls_count > 0` の日**。土日と 0 件の平日は除外する（祝日は除外しない。国別設定に判定を依存させないため）
- 母数が 20 日未満（bot_daily_cv_min_days）のメンバーは ③ を**判定不能**とし、発火扱いにしない
- CV = 母集団標準偏差（n で割る）÷ 平均。標本標準偏差（n−1）は使わない
- 閾値 0.25 は実測由来の暫定値。CV 単独では分離できない bot の実例があるため、④ ⑤ の補助 2 条件による検知と併用する
- 閾値の境界 ±0.1 に収まる判定はレポートに注記する（閾値の由来と再校正時の前提は `knowledge/design_notes.md`）

検知したメンバーの扱い:

- メンバー別シグナル（S2 / S3 / S6 / S8 / S12）の母数から除外する。S3 のアクティブレビュアー数・reviews_created の share、S8 の stddev と 0% メンバー数はいずれもクライアント側で数えるため、**除外を反映して再計算する**
- 除外したメンバー・該当した条件・除外による閾値の変化（例: アクティブレビュアー 9 名 → 8 名で S3 閾値 33.3% → 37.5%）をレポートに明記する
- **補助条件が 1 つしか成立しないメンバーは除外しない**。人間名義で PR もレビューも多い等の確信が持てない境界例と同様に、「取れていない情報」章に判断保留として列挙する

**限界（レポートに明記する）**: S2 / S6 の閾値基準になる team avg は get_team_stats が返す値で、**bot を含んだまま**提供される。メンバー別値からの再計算は母集合が異なるため代替にならない。したがってクライアント側でできるのは「判定される側（個人）の除外」までであり、bot を1名以上検知した場合は `team avg が bot を含むため S2 / S6 の相対閾値が歪んでいる可能性` を注記する

### プロバイダ別の AI 検出対応

| プロバイダ | 扱い |
|---|---|
| GitHub / GitLab | 通常判定 |
| Bitbucket | 通常判定 + 検出精度の注記 |
| Backlog | AI 利用レポートの集計対象外のため S7〜S9 は判定不能 |

**プロバイダの確定方法**: データ取得手順のどのツールもプロバイダを返さない（`get_monitorings` は monitoring 名のみ、`get_team_repositories` は repo_id / repo_name のみで、repo_name は `org/repo` 形式のためホストを判別できない）。したがって**プロバイダは推定しない**。ユーザーが明示した場合にのみ上表を適用し、未確定のままなら免責 3 に「プロバイダ未確定」と記載する。

未確定でも AI 系の判定自体は「AI 系共通前提」（チームの total_pulls_count > 0）で守られ、集計対象外のプロバイダなら判定不能に落ちる。ただし理由が分からないままになるため、**total_pulls_count = 0 で判定不能になった場合は「プロバイダが AI 利用レポート非対応の可能性」を理由の候補として併記する**。

### 発火シグナルの根拠強化（発火時のみ）

発火したシグナルの根拠を具体化する工程。**シグナルの判定そのものには使わない**（判定は各シグナルの定義・ガードで完結し、この工程の結果で判定を覆さない）。

**トレンド分類**: チーム値の月次推移が取れる指標のシグナル（S1 / S4 / S7 / S9 / S10 / S11）が発火した場合、該当指標の 6 バケット（S7 / S9 は #7 の月次 AI 率、それ以外は #3）を併記し、以下のいずれかに機械的に分類して根拠に添える。

指標ごとの**悪化方向**（分類はこの向きを基準にする）:

| 悪化方向 | 指標（シグナル） |
|---|---|
| 増加が悪化 | avg_lines_changed_per_pr（S1）/ lead_time_approval_to_merge（S4）/ unreviewed_merge_rate（S10） |
| 減少が悪化 | 月次 AI 率（S7 / S9）/ prs_merged ÷ prs_created（S11） |

- 継続悪化: 直近 3 バケットが悪化方向に**狭義単調**（同値を含まない）で推移している
- スパイク: 直近 3 バケットのうち 1 つだけが突出している。増加が悪化の指標は「そのバケット ÷ **残りのバケット**の最大値 > 1.5」、減少が悪化の指標は「そのバケット ÷ **残りのバケット**の最小値 < 1/1.5」。かつ継続悪化に当てはまらないこと。「残りのバケット」は対象バケットを除いた**取得できた全バケット**を指す（6 個揃うとは限らないため件数を固定しない）。比較対象が 0 の場合は分類できないため「変動」に倒す
- 変動: 上記のいずれにも当てはまらない

バケットが 3 つ未満しか得られない場合（新設チーム等）は分類せず「トレンド分類不能（バケット数 N）」と記載する。分類基準に無い解釈を足さない。メンバー別シグナル（S2 / S6）は個人の月次チーム統計が取れないため対象外。S12 は定義自体が月次推移のため対象外。

**リポジトリ別ドリルダウン**: S1 または S10 が発火した場合、リポ別の値から牽引リポを特定して課題マップの根拠に記載する。cur 側の値は #6 に同梱済みのため、追加で呼ぶのは S1 の prev 側だけ。

- S1: #6 の cur 値（`avg_lines_changed_per_pr` / `prs_created`）に加え、リポごとに prev（`start_date`=前期開始・range=quarter・`repository_ids`=[そのリポ]）を 1 回呼ぶ。cur の prs_created = 0 のリポは増加の牽引になり得ないため prev を省略する。並び順は「Δ（cur − prev）× cur の prs_created」の降順、記載は**上位 3 リポまで**
  - **prev の prs_created = 0 のリポ（当期に新設・稼働開始したリポ）は Δ を算出できない**。`avg_lines_changed_per_pr` は PR が 0 件だと 0 で返るため、そのまま引くと「0 からの増加」という誤った Δ になり、牽引リポの順位を歪める。該当リポは順位付けから除外し、**cur の値と PR 数だけを「取れていない情報」章に列挙**する（当期の変更行数が大きければ実質的な増加要因ではあるため、伏せない）
- S10: #6 の cur 値（`unreviewed_merge_rate` / `prs_merged`）を使い、追加の呼び出しは行わない。並び順は「unreviewed_merge_rate × prs_merged」の降順、記載は**上位 3 リポまで**
- prs_created（S10 では prs_merged）< 20 のリポは、値の解釈に注意が要る旨を添える
- **呼び出し数の上限**: S1 の prev はリポ数に比例するため、cur の prs_created 上位 20 リポに限定する。打ち切った場合は対象外にしたリポ数を「取れていない情報」章に記載する
- **入力が無い scope での扱い**: scope=monitorings はリポ一覧（#5）を取得しないためドリルダウンを行わない。scope=repos / members は #3 を取得しないため #3 由来のトレンド分類（S1 / S4 / S10 / S11）を行わない（#7 由来の S7 / S9 のトレンド分類は scope=members でも可能）。いずれも省略した旨を「取れていない情報」章に記載する

### 課題マップの生成

発火したシグナルを課題ラベルに変換し、カテゴリで束ねる。語彙はシグナル定義表の「課題ラベル」「カテゴリ」列を正とする。各課題には根拠（発火シグナル ID・実測値 vs 閾値・対象のメンバー / リポジトリ）を添付する。

```
- <カテゴリ>
  - <課題ラベル>: 根拠（Sx: 実測値 vs 閾値、対象）
```

### Skills 提案の生成（propose_skills）

**この工程は独立した関数境界として扱う。入出力を以下に限定し、他の工程への依存を持ち込まない**（将来、生成ロジックをサーバ側に差し替えるための境界）。

- 入力: ① 課題マップ（課題ラベル + 根拠）② ナレッジ（skill_catalog.md の内容）
- 出力: 提案リスト（提案エントリ ID / 課題ラベル / 提案名 / 形態 / ベースにする既存 Skill / 期待効果 / 導入手順）
- 制約:
  - 提案は必ずナレッジに grounding する。ナレッジに対応エントリの無い課題ラベルは「提案なし（ナレッジ未整備）」と明示する
  - 期待効果は発火シグナルの指標で記述する（次回診断がそのまま効果検証になる形）
  - **提案エントリ ID は決定的に組み立てる**: `<課題ラベル>::<ベース Skill>`。診断間の比較にこの ID を使うため、以下を厳密に守る（自由命名・恣意的な取捨選択を禁止する）
    - ID に入れるベースは、`knowledge/skill_catalog.md` の該当エントリの「ベース・参考にする既存 Skill」の**先頭項目に列挙されたものだけ**とする。`運用実績:` が付いた項目は補助的な実例なので **ID には含めない**（レポートの「ベースにする既存 Skill」列には従来どおり全て載せる）
    - 先頭項目に複数ある場合は名称を辞書順にソートして `+` で連結する。**辞書順は Unicode コードポイント昇順**とする（日本語名が並ぶと五十音順との解釈違いで ID が揺れるため）
    - ベース Skill 名はカタログの表記をそのまま使い、言い換え・省略をしない
    - 同一の課題ラベルに複数の提案を出す場合のみ末尾に `#2` `#3` を付ける
    - 例: `individual-review-latency::self-reviewer+update-self-review-checklist`（`運用実績:` の custom-reviewer 等は ID に入れない）
    - **カタログの `出発点にする sample` は ID に含めない**（sample を足しても ID が変わらないようにするため）
  - カタログの該当エントリに `出発点にする sample` がある場合、**導入手順の先頭でそのパスを示す**（例: 「① `samples/individual-review-latency.md` をコピーし、該当メンバーの直近レビューコメントから抽出した観点を `<!-- FILL -->` に埋める」）。sample はプレースホルダ入りのテンプレートで、そのままでは動かない

### レポート構成

冒頭に必ず記載する免責:

1. 閾値は複数組織の実データ由来の暫定値であり、実行時に上書き可能であること
2. 診断対象 monitoring の選定方法（指定された名前・fuzzy 解決の結果。同一チームに複数 monitoring がある場合はどれを選んだか）
3. プロバイダ別の AI 検出対応状況（該当プロバイダのみ）
4. データ集計遅延により直近2日を除外していること
5. p50 / p90 は Team+ API のサーバ側 percentile 集計値であること（算出方法の詳細は非公開）

章立て。**1・2・7・8・9 章は scope に関わらず必ず出力する**（当期のチーム統計 #2 はどの scope でも取得し、課題マップ・Skills 提案・取れていない情報は診断の結論そのものであるため。これらを落とすと「再現性の担保単位」の主判定が scope 指定時に定義できなくなる）。scope で増減するのは 3〜6 章だけで、monitorings → 3章 / repos → 5章 / members → 4・6章 を加える（scope=all は 1〜9 章すべて）。**見出しは「見出し文字列」列の値をそのまま使い、説明を書き足さない**（`## 1. 診断サマリ` の形式。診断間の比較に見出しを使うため）:

| # | 見出し文字列 | 中身 |
|---|---|---|
| 1 | 診断サマリ | 発火シグナル一覧 |
| 2 | スナップショット | 当期のチーム統計 |
| 3 | 月次推移 | 直近 6 完結暦月の推移 |
| 4 | メンバー別 | メンバー別の指標とシグナル該当者 |
| 5 | リポジトリ別 | リポ別 n_reviewed / p50 / p90 |

「1. 診断サマリ」の先頭には、以下 3 行を**この書式のまま**必ず出力する（診断間の比較を機械的に行うため）。

```
シグナルセット: v2
発火シグナル ID 集合: {S2, S6}
判定対象外: {S5}
```

- 「シグナルセット」は本 SKILL.md のシグナル定義の版。ID 集合の比較は同一版の診断間でのみ有効で、版が異なる診断と比較する場合は両版に共通するシグナルに限定し、その旨を注記する
- **版を上げる条件**: シグナルの追加・削除、既定閾値の変更、判定ガードの変更、指標の算出規定の変更のいずれかを行ったら版を上げる。文言整理・根拠説明の追記など、同じ入力から同じ発火集合が出る変更では上げない。実行時の thresholds 上書きは版に影響しない（同一版のまま、上書きした値をレポートに明記する）
- ID は昇順に並べる。該当が無ければ `{}` と書く（「なし」等に言い換えない）
- 「判定対象外」はガード・scope・前提チェックにより判定しなかったシグナル。不発火（判定した上で閾値未満）とは区別する
- 「8. Skills 提案」の表には提案エントリ ID の列を置く

### 再現性の担保単位

同一チームを繰り返し診断したとき、何が一致していれば「同じ診断結果」とみなすかを定義する。

- **主判定**: 発火シグナル ID 集合と提案エントリ ID 集合。診断の結論そのものであり、ここが一致することを再現性の要件とする。ただし比較は同一シグナルセット版の診断間でのみ成立する（版が異なる場合は共通シグナルに限定して比較する）
- **参考値**: メンバー単位・リポジトリ単位の該当者、および全ての実数値。母数が小さいチームでは 1 件の増減で一致率が大きく振れ、その多くは実データの変化に判定が追随した結果であるため、一致は要求せず記録に留める
- 参考値に差分が出た場合は、実データの変化か判定ロジックの揺れかを切り分けて注記する

### 「取れていない情報」章に必ず含めるもの

判定できなかったもの・判定対象外だが見落とすと診断が歪むものを列挙する。いずれも**発火扱いにはしない**。

### エラー・欠損時の原則

1. **単発の呼び出しの失敗は 1 回だけ再試行する**。#6（リポごと）・#8（ページごと）・ドリルダウンの prev のように同種の呼び出しを多数繰り返す工程では、1 件の一時的な失敗で全体を止めない。再試行しても失敗した場合は、その 1 件を欠損として扱って続行し、対象（リポ名・ページ番号）を「取れていない情報」章に記載する
2. **前提を壊す失敗は中断する**。monitoring 名の解決（#1）の失敗、認証・権限のエラー、当期のチーム統計（#2）の取得失敗は、以降の判定がすべて成立しないため、再試行せず状況を報告してユーザーに指示を仰ぐ
3. 部分欠損（メンバー不一致・件数不足による判定不能等）は「取れていない情報」章に列挙する
4. ユーザーへの対話補完は、提案精度に影響する欠落の場合のみ行う
