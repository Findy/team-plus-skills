# team-plus-capital-diag

組織の開発資本スコアを org → サブカテゴリ → チームの順にブレイクダウンし、「どの領域を・どのチームから」改善に着手すべきかを決めるための薄いトリアージレポートを出力する。

本 skill と team-plus-impl-diag の役割分担: **capital-diag は組織横断のトリアージ（ルーター）、impl-diag は特定チームの実装フェーズ（コミット〜マージ）の深掘り**。capital-diag はチームの課題そのものを診断せず、深掘り先への接続（次アクション）を提案するところまでを担う。impl-diag の自動起動はしない。

## 使いどき

「開発資本スコアで診断して」「組織の弱い領域を特定して」「どのチームから改善すべき？」「capital-diag」などで起動する。特定チームの実装プロセスの課題を深掘りしたい場合は本 skill ではなく team-plus-impl-diag を使う。

## 入力

| 引数 | 必須 | 既定 | 説明 |
|---|---|---|---|
| target_teams | ○（データ解決順で補完可） | - | 牽引チーム特定の対象にするチーム（monitoring 名）のリスト |
| period | - | 最新確定月 | スコア基準月 YYYYMM |

## データ解決順

1. 実行時の引数・ユーザー指示
2. 個人 memory: `~/.claude/team-plus-capital-diag/memory.yml`（存在すれば。`target_teams:` に monitoring 名のリストを持つ）
3. いずれにも無ければ `get_monitorings` の一覧を提示し、対象チームをユーザーに選んでもらう

**全 monitoring の走査はしない**。`get_monitorings` の一覧には個人用・検証用・期間や範囲違いの重複ビューが混ざり、開発資本スコアの集計対象（チーム連携済みの monitoring）かどうかは一覧からは判別できない。走査すると呼び出し数が monitoring 数に比例して跳ね、重複ビューが混ざって牽引チームの順位の意味も壊れる。組織の「チームの集合」を知っているのは利用者であり、対象リストは入力として受け取る。

## 実行手順

1. データ解決順に従って入力を確定する
2. 以下の「診断コア」を順に実行する
3. レポートを Markdown で出力する（保存先の指定があればファイルに保存）

データ取得の着手時に、これから行う呼び出し数の見込み「2（org スコア + monitoring 一覧）+ 対象チーム数」を報告する（monitoring 一覧をデータ解決に使わない場合は「1 + 対象チーム数」）。

## 診断コア

### スコープと必須ルール

- 数値・スコアは必ず Team+ MCP で取得する。他のデータソースからの代替推定はしない
- 開発資本スコア API は α 提供であり、スコア定義・メトリクス・レスポンスフィールドは予告なく変わりうる。**レスポンスの `warnings` に含まれる α 免責は、必ずレポートの免責に転記する**
- アウトプットはトリアージレポートと次アクションの提案まで。impl-diag その他の skill の自動起動、および提案の実行は利用者判断（本診断のスコープ外）

### 基準月の確定

- `get_org_capital_score` を **months=6・period 省略**で 1 回呼ぶ。返った最新の `period` を「スコア基準月」とし、それ以前の月は推移の文脈にのみ使う（判定には使わない）。呼び出しは 1 回で済むため、判定用と文脈用を分けて呼ばない
- スコアは毎月 1 日のバッチで前月分が確定する。したがってスコア基準月は原則「実行月の前月」、月初のバッチ実行前は「前々月」になる。**「今の状態」より最大で約 2 ヶ月古いスナップショットである**ことをレポートに明記する
- `period` 引数が指定された場合はそれを終端として同様に呼ぶ
- レスポンスが空（org のスコアが存在しない）の場合は診断を始めず、状況を報告してユーザーに指示を仰ぐ
- **以降のチーム別呼び出しは全て `period` = スコア基準月・`months=1` に固定する**。チームごとに最新確定月が異なりうるため、`period` を省略すると比較の基準月が揃わない

### 弱いサブカテゴリの判定

- スコア基準月の **9 サブカテゴリの score の最低値**を「弱い」とする。カテゴリ（3 分類）の score は判定に使わない（カテゴリは配下サブカテゴリの合成で、強い項目が弱い項目を打ち消して埋もれるため）
- 絶対閾値は置かず、組織内の相対順位で決定的に決める。**同率タイは全採用**する（タイブレークで 1 つに絞ると恣意的な規定が増え、捨てた側の情報が見えなくなる）。9 サブカテゴリすべて同値の場合のみ「判定不能」とし、「取れていない情報」章に回す
- `ranking`（elite / high / medium / low）は**判定に使わない**。ranking はベンチマーク閾値由来の水準ラベルであり、4 段階では粗すぎて順位付けに使えないため。レポートには文脈として併記する

### 牽引チームの特定

- 対象チームごとに `get_team_capital_score`（`period` = スコア基準月・`months=1`）を呼び、**弱いサブカテゴリの score の昇順**に並べて牽引チームを特定する
- **同値は同順位として全列挙し、恣意的なタイブレークをしない**。メトリクスの score は 4 値（100 / 75 / 50 / 25）+ null に量子化されており、サブカテゴリ score はその平均のため、チーム間の同値は頻発する。これは異常ではない
- **対象チームすべてが同値の場合は「牽引チームを特定できない（対象チーム間で同水準）」と明記し、「取れていない情報」章に回す**（実際に起きる。単一メトリクスのサブカテゴリでは全チームが同じ score に量子化されやすい）。根拠メトリクスの `value` は併記して読み手の判断材料にするが、**`value` による機械的な順位付けはしない**（メトリクスごとに良し悪しの向きが異なり、判定を metric_key に依存させない方針と矛盾するため）
- 根拠として、各牽引チームの該当サブカテゴリ配下のメトリクス（`metric_key` / `value` / `score`）を score の昇順で添える
- **`score: null` は「算出不能（未連携・母数なし）」であり 0 とは区別する**。`value` が 0 でも `score` が null のケースが実在する。レポートでは `-` と表記し、0 と混同しない
- `capital_scores: []`（空配列）で返るチームは「スコアなし」として順位付けから除外し、「取れていない情報」章に列挙する。原因は集計閾値（working members 2 名以上かつ PR 10 件以上）未満・チーム未連携・期間外のいずれかだが、**レスポンスからは区別できない**ため断定しない
- `working_members_count` を文脈として併記する（少人数チームはスコアが振れやすい）

### サブカテゴリ → 次アクション対応表（対応表版 v1）

弱いサブカテゴリに応じて次アクションを決める。**対応はサブカテゴリ単位で固定し、metric_key に依存させない**（α 提供でメトリクスセットは再編されうるが、サブカテゴリ構成の方が安定しているため）。

| サブカテゴリ | 次アクション |
|---|---|
| speed_making / control_structural / control_process | **impl-diag の実行を提案**（下記「impl-diag への接続書式」） |
| quality_rework | impl-diag の実行を提案する。ただし**この領域のメトリクス（手戻り率・コメント数等）に直接対応する impl-diag のシグナルは無い**旨を提案に明示する（impl-diag はレビュープロセスの周辺シグナルから間接的に迫る位置づけになる） |
| speed_shipping / speed_learning | impl-diag のスコープ外（デプロイ・イシュー管理系）。Team+ の DevOps 分析・サイクルタイムの画面での確認を案内する |
| quality_production_quality | impl-diag のスコープ外（インシデント系）。Team+ のインシデント関連データでの確認を案内する |
| quality_maintainability / control_complexity | impl-diag のスコープ外（コード品質系）。Team+ のコード品質分析の画面での確認を案内する |

### impl-diag への接続書式

弱いサブカテゴリが impl-diag 接続対象の場合、牽引チームの**上位 3 チームまで**（同率は全採用）に対して、次の書式で提案する。

```
次アクション: `impl-diag <チーム名>` を実行（期間・scope は impl-diag の既定に従う）
```

- 提案するだけで自動起動はしない
- capital-diag のスコア基準月（暦月スナップショット）と impl-diag の診断窓（実行日基準の 90 日ローリング）は定義が異なる。impl-diag の結果と資本スコアの値を直接突き合わせないよう、提案に一言添える

## レポート構成

冒頭に必ず記載する免責:

1. 開発資本スコア API は α 提供であること（レスポンス `warnings` の内容を転記）
2. スコア基準月と、実行時点とのラグ（原則、実行月の前月。月初のバッチ実行前は前々月）
3. 対象チームリストの選定方法（データ解決順のどれで決まったか。指定リスト・memory・ユーザー選択のいずれか）
4. スコアなし（空レスポンス）のチームと、その原因がレスポンスからは区別できないこと

章立て（見出しは「見出し文字列」列の値をそのまま使う）:

| # | 見出し文字列 | 中身 |
|---|---|---|
| 1 | トリアージサマリ | 機械比較用ヘッダ（下記）と結論 1〜2 行 |
| 2 | 組織スコア概観 | スコア基準月の 9 サブカテゴリ score / ranking と、直近 6 ヶ月の推移（文脈） |
| 3 | 牽引チーム | 弱いサブカテゴリのチーム別 score 昇順表 + 根拠メトリクス |
| 4 | 次アクション | 対応表に基づく提案 |
| 5 | 取れていない情報 | 判定不能・スコアなしチーム・その他の欠損 |

「1. トリアージサマリ」の先頭には、以下 3 行を**この書式のまま**必ず出力する（診断間の比較を機械的に行うため）。

```
対応表版: v1
スコア基準月: 202608
弱いサブカテゴリ集合: {quality_maintainability}
```

- 集合は昇順（Unicode コードポイント昇順）に並べ、該当が無ければ `{}` と書く
- レポート全体は表とサマリ中心の**1 画面程度**に収める。メトリクスの網羅的な展開・チーム別の全サブカテゴリ表など、トリアージの結論に効かない詳細は載せない（深掘りは impl-diag と Team+ 画面の役割）

## 再現性の担保単位

- **主判定**: 弱いサブカテゴリ集合。同一のスコア基準月・同一の対応表版の診断間で一致することを再現性の要件とする（スコアは月次確定・遡及再計算なしのスナップショットのため、同一基準月なら入力は不変）
- **牽引チームの順位**: 対象チームリストが同一の場合にのみ比較する。リストが異なる診断間では比較せず、その旨を注記する
- 対応表版が異なる診断間は次アクションを比較しない

## 版管理

- 「対応表版」は本 SKILL.md の判定規定と対応表の版。**版を上げる条件**: サブカテゴリ構成の変更への追随、対応表のアクションの変更、弱いサブカテゴリ・牽引チームの判定規定の変更のいずれかを行ったとき。文言整理・説明の追記など、同じ入力から同じ判定が出る変更では上げない
- API 側のメトリクス再編（メトリクスの追加・削除）だけでは版を上げない（判定はサブカテゴリ score で行い、metric_key に依存しないため）

## エラー・欠損時の原則

1. チーム別呼び出しの単発の失敗は 1 回だけ再試行する。再試行しても失敗した場合はそのチームを欠損として続行し、「取れていない情報」章に記載する
2. org スコアの取得失敗・空レスポンスは前提が成立しないため中断し、状況を報告してユーザーに指示を仰ぐ
3. スコアなし（空配列）のチームはエラーではない。「取れていない情報」章に列挙する
